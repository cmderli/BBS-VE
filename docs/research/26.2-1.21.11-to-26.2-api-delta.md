## 0. Executive summary — the changes that dominate the port

1. **`MultiBufferSource` and `Tesselator` no longer exist in 26.2.** They were removed from the jar
   entirely (`find /tmp/mcapi/full -name 'MultiBufferSource*'` and `-name 'Tesselator*'` → no results;
   `grep -rl 'MultiBufferSource' /tmp/mcapi/full --include='*.class'` → no results). All vertex-stream
   rendering goes through the **submit-node** architecture: `SubmitNodeCollector` /
   `OrderedSubmitNodeCollector`, with custom geometry via
   `SubmitNodeCollector.submitCustomGeometry(PoseStack, RenderType, CustomGeometryRenderer)`.
2. **`net.minecraft.client.gui.GuiGraphics` no longer exists.** Yarn `DrawContext`'s official name was
   `GuiGraphics`; in 26.2 the class is **`net.minecraft.client.gui.GuiGraphicsExtractor`** and the whole
   GUI pipeline was split into *extract* (record into `GuiRenderState`) and *render*
   (`net.minecraft.client.gui.render.GuiRenderer`). Method names changed too
   (`drawString`→`text`, `renderItem`→`item`, …).
3. **`RenderPipeline` was restructured significantly**: single blend/write-mask/depth-test fields were
   replaced by `ColorTargetState[]` (up to 8 MRT targets), `DepthStencilState`, `BindGroupLayout[]`,
   `VertexFormat[]` (per-buffer), and `PrimitiveTopology`. `LogicOp`/`colorLogic` and
   `DepthTestFunction` are gone; `CompareOp` is new.
4. **Frame presentation moved off `RenderSystem`**: `RenderSystem.flipFrame` is gone; 26.2 uses
   `com.mojang.blaze3d.systems.GpuSurface` (`acquireNextTexture` → `blitFromTexture` → `present`)
   driven from `Minecraft.renderFrame(boolean)`.
5. **Frame presentation moved off `RenderSystem`**: `RenderSystem.flipFrame` is gone; 26.2 uses
   `com.mojang.blaze3d.systems.GpuSurface` (`acquireNextTexture` → `blitFromTexture` → `present`)
   driven from `Minecraft.renderFrame(boolean)`, and the backend is runtime-selectable OpenGL **or
   Vulkan** (`net.minecraft.client.PreferredGraphicsApi`, new in 26.2).

Two important "smaller" breaks that touch a lot of call sites:
* `Minecraft.getMainRenderTarget()` → `GameRenderer.mainRenderTarget()`;
  `Minecraft.renderBuffers()` → `GameRenderer.renderBuffers()`;
  `Minecraft.setScreen(Screen)` → `Minecraft.setScreenAndShow(Screen)`;
  `Screen.render(GuiGraphics,…)` → `Screen.extractRenderState(GuiGraphicsExtractor,…)`.
* `net.minecraft.client.renderer.entity.ItemRenderer` is **gone**, replaced by
  `ItemModelResolver` / `ItemStackRenderState` / `SubmitNodeCollector.submitItem(...)`; and
  `net.minecraft.client.render.built`-era `Tesselator` is **gone**, so mesh building starts at
  `new BufferBuilder(ByteBufferBuilder, PrimitiveTopology, VertexFormat)`.

**Correction to a common assumption:** stencil is **not** a 26.2 regression. It is absent from the
1.21.11 API in exactly the same way (0 occurrences of "stencil" in all 10291 classes of the 1.21.11
client jar, in Yarn, and in intermediary). See §9.1.

Note: 26.2 is **not** a small delta from 1.21.11 in the renderer — but much of the "GPU abstraction"
(`GpuDevice`, `RenderPass`, `CommandEncoder`, `FrameGraphBuilder`, `RenderPipeline`, `PostChainConfig`,
`MultiBufferSource`-free submit pipeline) **already existed in 1.21.11** under the same names. The
1.21.11→26.2 delta is the *second* wave of that refactor: removal of the immediate-mode buffer layer,
the GUI extract/render split, the surface/present rework, the stencil/MRT pipeline state model, and
the addition of the Vulkan backend.

### 7.3 Can a mod register its own post effect in 26.2?

**Yes, via the resource-pack path — not via a registry.**
* There is **no post-effect registry**: `javap -p net.minecraft.core.registries.Registries | grep -i 'POST\|EFFECT'`
  returns only `CONSUME_EFFECT_TYPE`, `ENCHANTMENT_*_EFFECT_TYPE`, `MOB_EFFECT`. No `POST_EFFECT`.
* The loader is a resource-reload listener:
  `net.minecraft.client.renderer.ShaderManager extends SimplePreparableReloadListener<ShaderManager$Configs>`;
  `javap -c -p ShaderManager` shows constants `String post_effect`, `String shaders`,
  `String shaders/include/` and `POST_CHAIN_ID_CONVERTER = FileToIdConverter.json("post_effect")`
  (from `ldc_w #564 // String post_effect` + `FileToIdConverter.json`).
* `ShaderManager.loadPostChain(Identifier, Resource, ImmutableMap$Builder<Identifier, PostChainConfig>)`
  parses every `assets/*/post_effect/*.json` in the resource manager, and
  `public PostChain getPostChain(Identifier, Set<Identifier>)` returns the compiled chain.
* So a mod ships `assets/<modid>/post_effect/<name>.json` plus `assets/<modid>/shaders/post/*.fsh`
  and `assets/<modid>/shaders/core/screenquad.vsh` (or reuses `minecraft:core/screenquad`),
  then calls `Minecraft.getInstance().getShaderManager().getPostChain(id, Set.of(targets))`.
* **Activating** it on the main render target still requires more: `GameRenderer.setPostEffect(Identifier)`
  is **private** (`javap -p` → `private void setPostEffect(net.minecraft.resources.Identifier);`); the
  public surface is `clearPostEffect()`, `togglePostEffect()`, `processBlurEffect()`,
  `checkEntityPostEffect(Entity)`, `currentPostEffect()`. These are common access-widener/mixin targets.
* Fabric API 0.153.0+26.2 does **not** expose a post-effect API
  (`unzip -l fabric-rendering-v1-25.2.0.jar | grep -i PostEffect` → none). It does provide
  `LevelRenderEvents.*` and `SubmitRenderPhases.*` (see §6/§9 notes) but not post chains.

### 8.1 Where GLSL lives

```
ShaderManager.SHADER_PATH        = "shaders"                (ConstantValue: String shaders)
ShaderManager.SHADER_INCLUDE_PATH= "shaders/include/"       (ConstantValue: String shaders/include/)
ShaderType.VERTEX   = ("vertex",   ".vsh")

```
`ShaderType.idConverter()` bytecode (verified):
```java
public FileToIdConverter idConverter();
  new FileToIdConverter
  ldc  String shaders
  aload_0; getfield ShaderType.extension
  invokespecial FileToIdConverter.<init>(String, String)
```
i.e. `new FileToIdConverter("shaders", ".vsh"|".fsh")` — **any** subdirectory of `shaders/` is legal;
`core/` is only a convention. A pipeline's `withVertexShader("bbs:core/model")` /
`withFragmentShader("bbs:core/model")` resolves to `assets/bbs/shaders/core/model.vsh` / `.fsh`.
`ShaderManager.prepare` scans every resource pack; `isShader(Identifier)` + `loadShader(...)` pick up
mod shaders with **no registration**. 26.2 ships 61 files under `assets/minecraft/shaders/core/`
and 10 under `shaders/post/`.

**Startup caveat (verified):** `GameRenderer.preloadUiShader(ResourceProvider)` bytecode calls
`GpuDevice.precompilePipeline(RenderPipelines.GUI, …)`, `…GUI_TEXTURED…`, and (if Tracer is present)
`…TRACY_BLIT…` with a `ShaderSource` lambda that reads the shader file **raw**
(`ShaderManager.lambda$preloadUiShader$0(ResourceProvider, Identifier, ShaderType)`). It does **not**
run `GlslPreprocessor`. That is exactly why `gui.vsh`/`gui.fsh` carry the comment
`// Can't moj_import in things used during startup, when resource packs don't exist.` — a mod must not
make a startup-preloaded pipeline depend on `#moj_import`.

**Precompilation on reload (verified):** `ShaderManager.apply(ShaderManager$Configs, …)` bytecode:
```java
new HashSet<>(RenderPipelines.getStaticPipelines())    // RenderPipelines.getStaticPipelines()
RenderSystem.getDevice().clearPipelineCache();
for (pipeline : set) device.precompilePipeline(pipeline, shaderSource);   // -> CompiledRenderPipeline.isValid()
device.loadCriticalShaders();
```
So vanilla pipelines are all precompiled at resource-reload; a mod-built pipeline is compiled lazily on
first `RenderPass.setPipeline(...)` unless the mod calls the public
`GpuDevice.precompilePipeline(RenderPipeline)` / `(RenderPipeline, ShaderSource)` itself.

runtime — by shaderc→SPIR-V+SPIRV-Cross on Vulkan, and by the GL driver on OpenGL. A mod's GLSL must
therefore be acceptable to **both** paths.

### 8.3 `#moj_import` — exact syntax and resolution

`com.mojang.blaze3d.preprocessor.GlslPreprocessor` constant pool:
```
REGEX_MOJ_IMPORT = (#(?:\/\*(?:[^*]|\*+[^*/])*\*+\/|\h)*moj_import(?:\/\*…\*\/|\h)*(?:"(.*)"|<(.*)>))
REGEX_VERSION    = (#(?:\/\*(?:[^*]|\*+[^*/])*\+\/|\h)*version(?:\/\*…\*\/|\h)*(\d+))\b
```
Two forms, both accepted:
* `#moj_import <namespace:path>` → **absolute**; `ShaderManager$1.applyImport(boolean isRelative=false, String path)`
  bytecode: `Identifier.parse(path).withPrefix("shaders/include/")`. So
  `#moj_import <bbs:bbs_pixelart.glsl>` → `assets/bbs/shaders/include/bbs_pixelart.glsl`.
* `#moj_import "relative/path.glsl"` → **relative to the importing file's** `Identifier` via
  `parentLocation.withPath(...)`.

Other verified preprocessor facts: imports are **deduplicated** per shader (`Set importedLocations`,
`applyImport` returns `null` on a repeat); `#version N` is folded with `Math.max(N, current)` by
`processVersions`/`setVersion` and re-emitted as `#line %d %d\n%s`; failed imports log
`"Malformed GLSL import {}: {}"`; `GlslPreprocessor.injectDefines(String, ShaderDefines)` appends
`ShaderDefines.asSourceDirectives()` (this is how `RenderPipeline$Builder.withShaderDefine(...)` reaches
the shader).

**Include files shipped in 26.2** (`ls /tmp/mcapi/full/assets/minecraft/shaders/include/`):
`animation_sprite.glsl`, `chunksection.glsl`, `dynamictransforms.glsl`, `fog.glsl`, `globals.glsl`,

### 8.3.1 How post-effect passes build their own pipeline (bytecode-verified)

`net.minecraft.client.renderer.PostChain.createPass(TextureManager, PostChainConfig$Pass, Identifier)`
bytecode:
```java
RenderPipeline.builder(RenderPipelines.POST_PROCESSING_SNIPPET)
    .withFragmentShader(pass.fragmentShaderId())
    .withVertexShader(pass.vertexShaderId())
    .withLocation(<derived from pass>)
    .withBindGroupLayout(
        BindGroupLayout.builder()
            .withSampler(<input.samplerName()> + "Sampler")     // BootstrapMethods: "\u0001Sampler"
            .withUniform("SamplerInfo", UniformType.UNIFORM_BUFFER)
            .withUniform(<each key of pass.uniforms()>, UniformType.UNIFORM_BUFFER)

```
Two consequences a mod cannot ignore:
* the JSON `"sampler_name": "In"` becomes the GLSL uniform **`InSampler`** (name + literal `Sampler`);
* a `SamplerInfo` UBO (`vec2 OutSize; vec2 InSize;`) is **always** injected, then one UBO per key of the
  JSON `"uniforms"` object (e.g. `BlitConfig`, `InvertConfig`, `BlurConfig`). Uniform values are
  positional/std140 — `UniformValue$Vec2Uniform` etc. carry only a `value`, so the GLSL block field
  order must match the JSON array order.

### 9.17 Visibility of the backend classes (matters for mixins/access wideners)

`com.mojang.blaze3d.opengl.GlStateManager` is **public** and its raw-GL methods are `public static`.

### 9.19 Backend selection gates every raw-GL escape hatch

```
net.minecraft.client.PreferredGraphicsApi = { DEFAULT, OPENGL, VULKAN }   // NEW in 26.2
  public com.mojang.blaze3d.systems.GpuBackend[] getBackendsToTry();
```
`javap -c -p net.minecraft.client.PreferredGraphicsApi` → `getBackendsToTry()` constructs
`new GlBackend()` then `new VulkanBackend()` and switches on the `VULKAN` constant, so `DEFAULT` tries
**OpenGL first**. Selection is reachable from a CLI flag (`--graphicsBackend`, jopt
`OptionSpec<PreferredGraphicsApi>`), from `Options.preferredGraphicsBackend`, and from an
auto-probe (`VulkanBackend.checkBackendAvailable()` / `NativeLibrariesBootstrap.tryLoadingVulkan()`).
Consequence: `GLCapabilities` are created **only** in `GlDevice.<init>` (`GL.createCapabilities()`),
and `GlDevice` is constructed **only** by `GlBackend.createDevice`. If Vulkan is selected, `GlDevice`
is never built and no GL context exists — so **every raw `GL33C`/`GL43C`/`GL45C` call is invalid**.
Any raw-GL work (stencil §9.1, `glGetTexImage` §9.8, `glDepthRange` §9.11, compute §9.16, custom VAO
§9.12) must be gated on the active backend, or the mod must force OpenGL.
The whole `com.mojang.blaze3d.vulkan` package is **NEW**: `grep -c 'com.mojang.blaze3d.vulkan' client.txt`
→ `0`, 0 classes in the 1.21.11 jar, **69** classes in 26.2.

Raw `org.lwjgl.opengl.GL43.glDispatchCompute` is reachable on the GL backend but there is no
`GpuBuffer`-level compute plumbing (no SSBO binding API: `GpuBuffer` usages are `USAGE_VERTEX,
USAGE_INDEX, USAGE_UNIFORM, USAGE_UNIFORM_TEXEL_BUFFER, USAGE_INDIRECT_PARAMETERS, USAGE_MAP_READ,
USAGE_MAP_WRITE, USAGE_HINT_CLIENT_STORAGE, USAGE_COPY_DST, USAGE_COPY_SRC` — no `USAGE_STORAGE`).

### 9.21 Instancing / indirect — **EXPOSED, and largely NEW in 26.2**

26.2 `RenderPass` (verbatim, abridged to the draw calls):
```java
public void drawIndexed(int baseVertex, int firstIndex, int indexCount, int instanceCount, int baseInstance);
public void draw(int baseVertex, int firstVertex, int vertexCount, int instanceCount);
public void multiDrawIndexed(IntBuffer, int, int, int);
public void multiDrawIndexed(org.lwjgl.PointerBuffer, IntBuffer, IntBuffer, int);
public void multiDraw(IntBuffer, int, int, int);
public void multiDraw(IntBuffer, IntBuffer, int);
public void drawIndexedIndirect(GpuBufferSlice, int);
public void drawIndirect(GpuBufferSlice, int);
public <T> void drawMultipleIndexed(Collection<RenderPass$Draw<T>>, GpuBuffer, IndexType, Collection<String>, T);

```
**Novelty check (verified from the 1.21.11 jar):** 1.21.11 `RenderPass` is an *abstract* class whose
draw surface was only
```

public abstract <T> void drawMultipleIndexed(Collection<RenderPass$a<T>>, GpuBuffer, VertexFormat$a, Collection<String>, T);
```

— no `instanceCount`, no `baseInstance`, no `*Indirect`, no `multiDraw(IntBuffer,…)`.
`glVertexAttribDivisor` appears in **0** 1.21.11 class files (vs present in 26.2), and
`RenderPass.MAX_VERTEX_BUFFERS` / `RenderPass$Draw` with `firstIndex()/indexCount()/baseVertex()/slot()`
are 26.2 additions. `RenderPass` also changed from abstract to a concrete class backed by
`RenderPassBackend`. `VertexFormat.getStepRate()` / `VertexFormat.builder(int stepRate)` provide
per-instance attributes. `DeviceFeatures` (record) =
`shaderDrawParameters, multiDrawDirectInterleaved, multiDrawDirectSeparate, multiDrawIndirect,
drawIndirect, nonZeroFirstInstance, persistentMapping` (the last gates `firstInstance != 0`).
Note `glDrawElementsBaseVertex` (non-instanced) appears in 0 files — base vertex is only reachable
through the instanced variant.

### 9.22 Immediate-mode-style vertex building — **EXPOSED, but ctor changed**


`Tesselator` (the no-arg shared builder) is gone; a mod must own its `ByteBufferBuilder`.
For rendering inside the world, prefer `SubmitNodeCollector.submitCustomGeometry(...)`.

### 9.23 Raw LWJGL GL access — **available, GL backend only**

`org.lwjgl.opengl.GL33C.glReadPixels` is invoked from `GlStateManager._readPixels` bytecode, so LWJGL

`public` and still exposes (complete list from `javap -p`, `public static`):

## Confidence / gaps

### Method

Every claim in §§1–3, 6, 7, 8, 9 is backed by a command I ran myself against
`/tmp/mcapi/full` (26.2), `/tmp/mc12111/client.jar` + `client.txt` + `mappings.tiny` (1.21.11), and
cross-checked by a normalised two-way signature diff (`/tmp/mcapi_work/diffcls.py`,
`/tmp/mcapi_work/delta.py`) rather than by name matching alone. Where a delegated deep-dive reported
something I had not seen, I re-ran the `javap`/`grep` myself and only then added it — and the
delegated work corrected me twice, both incorporated above:

* **stencil was already absent in 1.21.11** (0 hits across 10291 class files, yarn, intermediary and
  official mappings) — so it is not a 26.2 regression (§9.1);
* **1.21.11's `VertexFormatElement` is already a record** (`id, index, Type, Usage, count`) and
  `VertexFormatElement$Type`/`$Usage` *do* exist there — what 26.2 changes is the record's components
  and the deletion of both enums (§3.3).

**Tooling defect found and fixed mid-report (disclosed for reproducibility):** my ProGuard parser
(`/tmp/mcapi_work/maps.py`) initially required a `line:line:` prefix to classify a mapping line as a
*method*, so **interface and abstract members without line numbers were filed as fields** — e.g.
`maps.official()['net.minecraft.client.DeltaTracker']['methods']` came back empty and
`Renderable.render(GuiGraphics,int,int,float)` was invisible. This affected only the 1.21.11 *official*
side of interface types. I patched the parser (`sig = m.group(3) if m else lhs`, then classify by the
`ret name(args)` shape) and **re-ran every diff in this report**. Two conclusions changed and are
corrected above: `DeltaTracker` itself is unchanged (3/3 methods), but `DeltaTracker$Timer` **lost
`advanceTime(long, boolean)`** (10 → 9); and `Renderable`'s 1.21.11 member really is
`render(GuiGraphics,int,int,float)`, now confirmed from the raw mapping line rather than inferred.
All class-level results (the great majority of this report) were unaffected, because classes carry
line numbers.

### What I could NOT verify

1. **1.21.11 method *bodies*.** 1.21.11 is obfuscated; I read its *signatures* from `client.txt`
   (ProGuard) and `mappings.tiny` (Yarn) and inspected its class *shape* with `javap` on the
   obfuscated classes, but never decompiled a 1.21.11 method body. All "behaviour changed" statements
   are inferences from signature/field/constant-pool changes plus 26.2 bytecode. In particular the
   claim that `LevelRenderer.renderLevel` became `LevelRenderer.render` rests on name + signature +
   parameter-type lineage, not on a call-graph proof.
2. **Vulkan backend at runtime.** I confirmed from bytecode that `VulkanRenderPipeline` never programs
   `VkStencilOpState`, that `GlslCompiler` uses shaderc (target env Vulkan 1.2) + SPIRV-Cross, and that
   `PreferredGraphicsApi.DEFAULT` tries OpenGL first. I did **not** launch the game on Vulkan, so I
   cannot confirm which backend a given machine selects, nor whether shaderc accepts every GLSL
   construct the GL driver accepts. **This is the single largest unverified risk for §8.**
3. **Multi-color-target (`ColorTargetState[>1]`) is untested in vanilla.** `MAX_COLOR_TARGETS = 8`,
   `GlCommandEncoder` builds `GL_COLOR_ATTACHMENT0 + i` and calls `glDrawBuffers`, and
   `DeviceLimits.maxColorAttachments()` exists — but no `RenderPipelines` entry uses more than one
   color target, so "MRT works" is a structural claim, not an observed one.
4. **Mip generation.** `glGenerateMipmap` is called by **zero** classes in either version;
   `MipmapGenerator.generateMipLevels(...)` computes `NativeImage[]` on the CPU and
   `createTexture(..., int mipLevels)` declares the chain. I did not verify that the GL backend uploads
   the generated levels rather than allocating uninitialised ones.
5. **`GlslCompiler` bind-group reflection details.** I confirmed which shaderc/spvc functions are called
   and that `addToBindGroup` matches reflected names against `BindGroupLayout$UniformDescription`, but
   I did not decode the exact name-mangling rules, so "what uniform name a mod must write in GLSL to
   match `withUniform("Name", …)`" is only partly established. (Vanilla's direct evidence: the
   `BindGroupLayouts` and `PostChain.createPass` bytecode pass the literal GLSL block names
   `DynamicTransforms`, `Projection`, `Globals`, `Fog`, `Lighting`, `ChunkSection`, `SamplerInfo`,
   `BlitConfig`, `InvertConfig`, `BlurConfig`, and sampler names `Sampler0…2` / `<input>Sampler`.)
6. **`#moj_import` relative-path resolution.** `applyImport(true, …)` uses `parentLocation.withPath(...)`;
   I did not decode the `InvokeDynamic` lambda that builds the new path, so the relative form's exact
   resolution (same-directory vs. `shaders/`-relative vs. `FileUtil.normalizeResourcePath` semantics)
   is unverified. The `<namespace:path>` absolute form **is** fully verified
   (`Identifier.parse(path).withPrefix("shaders/include/")`).
7. **`GuiRenderer` draw-ordering / stratum semantics.** I have the full method list and the
   `GuiRenderState` node/stratum API (`nextStratum`, `blurBeforeThisStratum`, `addDebugRectangleIfEnabled`,
   `findAppropriateNode`, `navigateToAboveHighestElementWithIntersectingBounds`), but not the exact
   ordering guarantees — which matter for a mod that interleaves 3D world rendering with GUI.
8. **Fabric API coverage.** I inspected `fabric-rendering-v1-25.2.0` (from `fabric-api-0.153.0+26.2.jar`)
   for `LevelRenderEvents`, `LevelExtractionEvents`, `SubmitRenderPhases`,
   `FabricRenderPipeline`, `FabricOrderedSubmitNodeCollector`, `LevelRenderContext` /
   `AbstractLevelRenderContext` / `LevelExtractionContext`, `PictureInPictureRendererRegistry`, and
   confirmed there is **no** post-effect API. I did **not** audit every other Fabric module
   (`fabric-screen-api-v1`, `fabric-transitive-access-wideners`, …) for 26.2-only helpers that could
   replace the mixins BBS currently uses.
9. **The 1.21.11 Yarn *source* of BBS.** The checkout at `/home/mizuki/Documents/BBSLE` is already
   partially migrated (`gradle.properties` targets `26.2` with `fabric.loom.disableObfuscation=true`,
   `build.gradle` has no `mappings` line and uses `implementation` not `modImplementation`,
   `bbs.accesswidener` header mentions 26.2) while `src/main/java` still imports Yarn names
   (`net.minecraft.util.Identifier`, `net.minecraft.item.ItemStack`, `net.minecraft.text.Text`,
   `net.minecraft.util.math.BlockPos`, …). I did **not** enumerate every Yarn symbol the source uses,
   so the tables here are organised by the requested topic list rather than by an exhaustive scan of
   BBS's imports. A complete symbol-level port list would need
   `grep -rhoP '^import net\.minecraft\.[A-Za-z0-9_.]+;' src/main/java | sort -u` piped through
   `/tmp/mcapi_work/maps.py`. **This is the main remaining gap if the goal is a line-by-line port
   checklist rather than an API delta.**
10. **Item rendering migration detail.** I confirmed `ItemRenderer` is removed and listed the
    replacement classes (`ItemModelResolver`, `ItemModels`, `ItemStackRenderState`,
    `TrackingItemStackRenderState`, `ModelRenderProperties`) plus
    `OrderedSubmitNodeCollector.submitItem(…)` and `GuiGraphicsExtractor.item(…)`, but did not map
    every `ItemRenderer.renderItem` call site's semantics onto `ItemModelResolver`/`submitItem`.
11. **Shader file diff completeness.** I diffed `gui.vsh`, `gui.fsh`, `position_color.vsh` (identical),
    `block.vsh` and `lightmap.fsh` (differ) myself, and a full `diff -rq` of the two shader trees was
    run and reported (11 differing files, 6 new, 15+ removed). I did not read every differing file
    line-by-line, so a change inside one of the other nine differing shaders could have been missed.
12. **Post-effect target identifiers.** I confirmed `PostChain.MAIN_TARGET_ID`,
    `ShaderManager.getPostChain(Identifier, Set<Identifier>)`, the private
    `GameRenderer.setPostEffect(Identifier)`, and the vanilla target accessors
    (`LevelRenderer.translucentTarget()/itemEntityTarget()/particlesTarget()/weatherTarget()/
    cloudsTarget()/entityOutlineTarget()`), but did not verify exactly which `Identifier` set a
    mod-supplied chain may legally reference (the loader validates `externalTargets` and throws
    `"Referenced external targets are not available in this context"`).
13. **Runtime behaviour of any 26.2 API.** Nothing in this report was executed in a running 26.2
    client. All statements are static-analysis facts (class presence, `javap` signatures, constant
    pools, `javap -c` control flow). "Exposed" means "a public signature exists and the bytecode path
    is present", not "a mod was observed using it successfully".

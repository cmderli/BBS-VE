# Film editor preview was a flat fill (26.2 port) — solved

## Symptom

The film editor's camera viewport (centre of the panel) drew a flat fill the colour of the editor
theme instead of the world. The panel, timeline, docks and buttons all rendered correctly.

Resolved. The flat fill was **the panel background showing through a snapshot texture that had never
been written to** — the blit that fills it issued a draw of zero indices. Two further bugs were
behind it, one of which made the previous session's one "fix" look like it had not worked, and a
fourth made the picture upside down once it did appear.

## The four bugs, in the order they hid each other

### 1. `RenderPass.drawIndexed` argument order (the flat fill itself)

26.2's signature is

```java
drawIndexed(int indexCount, int instanceCount, int firstIndex, int baseVertex, int firstInstance)
```

1.21.11's was `drawIndexed(int baseVertex, int firstIndex, int indexCount, int instanceCount)`. The
first two arguments swapped meaning, and the fifth is new. Six call sites were ported with the old
order, all of them as `pass.drawIndexed(0, 0, <indexCount>, 1, 0)` — which 26.2 reads as
`indexCount = 0, instanceCount = 0`, i.e. **draw nothing**.

Nothing about that fails: the pass is created, the pipeline binds, the vertex and index buffers are
set, the draw is recorded, the pass closes and submits. The target is simply left exactly as it was,
so the snapshot stayed a zeroed texture — RGBA(0,0,0,0) — and `GUI_TEXTURED` multiplies texel alpha,
so the preview drew nothing at all and the panel background showed through.

Verified against vanilla rather than guessed: `GuiRenderer.draw` calls
`drawIndexed(indexCount, 1, firstIndex, baseVertex, 0)`, and `VulkanRenderPass.drawIndexed` forwards
its five ints straight to `vkCmdDrawIndexed(cb, indexCount, instanceCount, firstIndex, vertexOffset,
firstInstance)`.

Fixed in `ScreenQuadPass` (the film snapshot blit, the multilink filter, the selection ants),
`BBSPickerRenderer` (×4), `Gizmo` and `BBSGeometryQueue`.

### 2. The read-back completion callback can never fire (why the export produced no file)

`CommandEncoder.copyTextureToBuffer` takes a `Runnable` to be called when the copy has completed.
On Vulkan that callback is not a fence the caller can wait on: `VulkanCommandEncoder` hands it to its
`DestructionQueue`, and that queue only runs its entries from `rotate()`, which happens **once per
`submit()`**, for the generation that has just retired.

So a read-back that submits and then blocks on a latch is waiting for something that can only happen
during the *next* submit — which the parked render thread will never issue. Every read-back timed out
and returned null: video frames, screenshots, the colour picker.

The previous session's `SUBMIT the read-back copy` commit fixed the first half (the copy really was
never being submitted) but not this half, so the symptom survived the fix and the conclusion drawn
from it ("the read-back was a real and separate bug, not this one") was only half right.

Fixed in `BBSGpu.submitAndAwait`: submit, then pump up to three more submits while the completion
latch is still counting down. Each `submit()` already waits for the generation two back, so the copy
has completed by the time the callback runs, and backends that deliver the callback inline (OpenGL)
pay nothing.

### 3. The snapshot was captured a frame early, and with the interface in it

`onRenderBeforeScreen()` — the hook that captured the snapshot for an open editor — runs from
`Hud.extractRenderState`, and 26.2's frame is **extract, then render**: `Minecraft.renderFrame` calls
`GameRenderer.extract` and only afterwards `GameRenderer.render`, which is where `renderLevel` (and
so the world) happens.

Capturing there therefore copied the framebuffer **before that frame's world had rendered**, and at
that point the framebuffer still held the previous frame's world *plus* the editor interface, which
is composited into it at the end of every frame (`GuiRenderer.draw` reads
`GameRenderer.mainRenderTarget()` then, and BBS has not swapped it back yet). With bug 1 fixed, the
preview showed exactly that: a small copy of the editor, one frame late, inside itself.

Fixed by moving the editor's capture to the end of the world render (`onWorldRenderEnd`), which is
the one point in a 26.2 frame that is both after the world lands in BBS's framebuffer and before the
interface is composited into it. The `toggleFramebuffer(false)` that `captureAndRestore` already ends
with then hands the interface phase the window framebuffer, which is what `onRenderBeforeScreen` used
to arrange one phase later.

### 4. The snapshot was upside down

The preview flipped V when drawing (`v1 = height, v2 = 0`) and the video recorder prepended `vflip`
to the ffmpeg filter chain. Both are the 1.21.1 convention: there the snapshot was filled by a raw
GL blit and read back with `glGetTexImage`, and both are bottom-up.

26.2's snapshot is filled by a device-neutral pass that samples the framebuffer's colour texture with
`v = 0` at its first row, and read back with `copyTextureToBuffer`, which returns that same row
first — so row 0 is the **top** of the frame on both backends. Measured, not assumed: the snapshot
correlates with the framebuffer (0.51 NCC) and not with its flip (0.003).

Fixed by dropping the flip in `UIFilmPreview` and the `vflip` in `VideoRecorder` (which now passes
the `null` filter, because `%FILTERS%` lands in the middle of an argument list and an empty
expansion would hand `-c:v …` to `-vf`). Verified end to end by piping a dumped frame through the
recorder's exact ffmpeg arguments and looking at the decoded frame.

## How it was actually found

Two things were missing from the previous round, and both were about measurement rather than
reasoning:

**A probe that could not report.** `dbgSamplePixels` still had the missing `submit()` (bug 2's first
half), and its guard was `pxProbe++ < 2` on a counter that every `captureAndRestore` call
incremented, editor open or not — so by the time the editor appeared the probe had already spent
itself. It printed nothing, and the silence was read as "nothing wrong here".

**No look at the pixels.** The three candidates listed in the previous version of this document
(cleared framebuffer / wrong source binding / world not in the target) are all answerable by reading
the two textures back and comparing them, which nothing had ever done.

So the working diagnostic is a dump, not a texel probe: `-Dbbs.dumpSnapshot=true` writes the
framebuffer (before the blit) and the snapshot (after it) out as raw RGBA8 with a min/max summary per
channel, on the first three frames of an open film panel, and reports every attempt whether it
succeeds or not. One look at the pair said "the framebuffer is fine, the snapshot is zeros" and
eliminated all three candidates at once:

```
[BBS dump] fb-2   2560x1350 -> /tmp/bbs-fb-2.raw   r[0..255] g[2..255] b[1..255] a[255..255]
[BBS dump] snap-2 1514x784  -> /tmp/bbs-snap-2.raw r[0..0]   g[0..0]   b[0..0]   a[0..0]
```

Read a dump back with, for example:

```
ffmpeg -f rawvideo -pix_fmt rgba -s 1514x784 -i /tmp/bbs-snap-1.raw /tmp/bbs-snap-1.png
```

`magick compare -metric NCC` between a dump and a scaled/flipped version of the other one is what
settles orientation questions without relying on the eye.

**A probe keyed on a counter is a probe that can expire.** Every diagnostic added since is keyed on
the state that matters (the film panel is showing) and prints unconditionally, including its
failures.

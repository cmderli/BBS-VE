# Porting BBS mod to Minecraft 26.2's GPU abstraction

This document is the working reference for the `26.2` branch. It records what Minecraft 26.2
actually is, what the port has already done, what every remaining OpenGL touchpoint in the mod has
to become, and in what order.

Everything marked **verified** below was checked against the real artifacts on this machine (the
unobfuscated 26.2 client jar, its version manifest, the Fabric metadata and the Fabric API jar), not
recalled from memory. Where a claim comes from an external source it is linked; where it is still
open it is listed under *Open questions* at the end.

## 2. What 26.2 changes for a mod like BBS

### 2.1 Minecraft ships unobfuscated, and there are no mappings any more

**Verified.** `~/.gradle/caches/fabric-loom/26.2/minecraft-client.jar` (the raw Mojang download)
contains `net/minecraft/client/Minecraft.class`, and none of its 10,952 classes has an obfuscated
name. The 26.2 version JSON has no `client_mappings` download at all.

Fabric's side matches:

* `net.fabricmc:yarn` stops at `1.21.11+build.6` (maven metadata `<release>`); there is no 26.x Yarn.
* `meta.fabricmc.net/v2/versions/loader/26.2` reports intermediary `0.0.0` — the identity mapping.
* Loom therefore runs with `fabric.loom.disableObfuscation=true`, takes no `mappings` dependency, and
  neither remaps the game nor the mod's own classes.

Two consequences that decide the whole port:

1. **A mod for 26.2 compiles against Mojang's own names**, so every Minecraft reference in BBS's
   1,566 source files has to move from Yarn to official names. That is mechanical but it is the
   gate: until it is done, `compileClientJava` reports "package net.minecraft.client.gl does not
   exist" for every file at once and says nothing about the real API deltas. §4 is about this.
2. **Fabric API is a plain `implementation` dependency** (`implementation "net.fabricmc.fabric-api:fabric-api:0.153.0+26.2"`),
   not `modImplementation`, and the same for the loader — there is no remapping step that a
   mod-flavoured configuration could feed.

### 2.2 The rendering backend: Vulkan exists, OpenGL is still the default in 26.2

From the 26.2 release notes and the Fabric developer documentation (external, see links at the end):

* Video Settings exposes **Graphics API: `Default` | `Prefer Vulkan (Experimental)` | `Prefer OpenGL`**,
  backed by `net.minecraft.client.PreferredGraphicsApi`. In 26.2, `Default` means **OpenGL**; the
  first 26.2 snapshot defaulted to Vulkan and the release moved it back.
* There is **no JVM flag or launch argument** for the backend: it is a game option, and changing it
  requires a restart. Startup falls back automatically (a Vulkan crash downgrades
  `Prefer Vulkan` → `Default` → `Prefer OpenGL`), and F3's system specs show which backend is live —
  which is also the only reliable way to confirm from a log what a test run actually used.
* Vulkan requires Vulkan 1.2 plus `VK_KHR_dynamic_rendering` and push descriptors; macOS goes
  through MoltenVK. OpenGL is slated for removal in a later drop — still selectable in 26.3, no date
  announced.
* Fabric's guidance is explicit that **raw OpenGL is not supported**: a mod has to render through
  Blaze3D. Vanilla's own GL calls are confined to `com.mojang.blaze3d.opengl.*` and use only
  `GL33C`; `GL11`/`GL20`/`GL30`/`GL45` appear nowhere in the game.

For BBS this has one important practical reading: **the port is not "write Vulkan code", it is
"stop writing OpenGL code"**. Everything in §5 goes through the backend-neutral device API, and the
same code then runs on both backends. A mod that reaches for `GL11` keeps working only while the
user has not switched to Vulkan.

> Testing note: the supported switch is the in-game Graphics API option, and it needs a restart.
> `runClient --args="--graphicsBackend VULKAN"` is what the Caustica 26.2 project in this workspace
> passes in development; no such flag is documented for 26.2, so treat it as a convenience and
> confirm the live backend in F3's system specs before trusting a test result.

### 2.3 The modder-facing API is a small explicit RHI

**Verified** by `javap` over the 26.2 jar. The pieces BBS cares about:

| Area | Classes |
|---|---|
| Device | `com.mojang.blaze3d.systems.GpuDevice`, `GpuDeviceBackend`, `GpuBackend`, `DeviceInfo`, `DeviceFeatures`, `DeviceLimits`, `SamplerCache`, `RenderSystem.getDevice()` |
| Recording | `CommandEncoder` (+`CommandEncoderBackend`), `RenderPass` (+`RenderPassBackend`), `RenderPassDescriptor`, `RenderPass.RenderArea`, `TransientMemory`, `GpuFence` |
| Pipelines | `com.mojang.blaze3d.pipeline.{RenderPipeline, RenderPipeline.Builder, RenderPipeline.Snippet, CompiledRenderPipeline, BindGroupLayout, BindGroupLayout.Builder, ColorTargetState, DepthStencilState, BlendFunction, BlendEquation, RenderTarget, TextureTarget, MainTarget}` |
| Textures | `com.mojang.blaze3d.textures.{GpuTexture, GpuTextureView, GpuSampler, AddressMode, FilterMode}`, `com.mojang.blaze3d.GpuFormat` |
| Buffers | `com.mojang.blaze3d.buffers.{GpuBuffer, GpuBufferSlice, GpuFence, Std140Builder, Std140SizeCalculator}` |
| Vertex | `com.mojang.blaze3d.vertex.{VertexFormat, VertexFormat.Builder, DefaultVertexFormat, PoseStack, BufferBuilder, MeshData, StagingBuffer, ByteBufferBuilder}` |
| Frame graph | `com.mojang.blaze3d.framegraph.{FrameGraphBuilder, FramePass}` — the vanilla frame is a graph of passes, and `net.minecraft.client.renderer.LevelTargetBundle` / `PostChain` hang off it |
| Shaders | `com.mojang.blaze3d.shaders.{ShaderSource, ShaderType, UniformType}`, `net.minecraft.client.renderer.ShaderDefines`, GLSL assets under `assets/<ns>/shaders/core`, post effects under `assets/<ns>/post_effect/*.json` |

Two details that make the port tractable:

* **GLSL is still the authoring language.** 26.2 ships 61 core shaders as `#version 330` `.vsh`/`.fsh`
  files, and the Vulkan backend compiles them at runtime
  (`com.mojang.blaze3d.vulkan.glsl.GlslCompiler` → SPIR-V via `lwjgl-shaderc`, with
  `SpvUniformBuffer`/`SpvSampler` doing the reflection). BBS's `assets/bbs/shaders/core/*` do not
  have to be rewritten in another shading language — but their uniform declarations do have to
  match the pipeline's bind group layout exactly, because the backend reflects the compiled module
  and checks it.
* **Vanilla's bind groups are public and reusable.** `net.minecraft.client.renderer.BindGroupLayouts`
  exposes `DYNAMIC_TRANSFORMS`, `PROJECTION`, `MATRICES_PROJECTION`, `FOG`, `GLOBALS`, `LIGHTING`,
  `SAMPLER0`, `SAMPLER1`, `SAMPLER2`, `SAMPLER0_SAMPLER1_SAMPLER2`, … so a BBS shader can declare
  `layout(std140) uniform DynamicTransforms { … };` and `Sampler0` verbatim and compose its
  pipeline out of those objects.
* **Vanilla's pipeline snippets are reachable from a mod, through Fabric API.**
  `RenderPipelines.register(...)` and every `RenderPipelines.*_SNIPPET` field are private in 26.2,
  but `fabric-transitive-access-wideners-v1` (bundled in Fabric API, 24 `RenderPipelines` entries in
  0.153.0+26.2) widens them for all mods, and `RenderPipeline.Snippet` has a public canonical
  constructor besides. **Verified by compiling**: a pipeline built from `RenderPipelines.ENTITY_SNIPPET`
  compiles against this project's own compile classpath. This is the safer way to define a pipeline
  whose shader must agree with vanilla — a snippet cannot disagree with vanilla about which bind
  groups the shader is compiled against — and it is how BBS's pixel-art pipelines are built in this
  branch (`BBSRenderPipelines.PIXEL_ART`, from `GUI_TEXTURED_SNIPPET`), which is a direct translation
  of the 1.21.11 `pixelArtPipeline(RenderPipelines.GUI_TEXTURED, "pixelart")`.

### 2.4 What no longer exists, and what that costs BBS

**Verified** against the jar:

* `net.minecraft.client.gui.GuiGraphics` (Yarn `DrawContext`) — **gone**. 26.2 extracts GUI draws
  (`GuiGraphicsExtractor`, `net.minecraft.client.gui.render.GuiRenderState`) and replays them
  (`GuiRenderer`, `TextureSetup`). Every BBS interface element that drew through `DrawContext` and
  every `Batcher2D` consumer sits on this.
* `net.minecraft.client.render.RenderLayer` / `RenderSetup` — replaced by
  `net.minecraft.client.renderer.rendertype.{RenderType, RenderTypes, PreparedRenderType}`;
  `PreparedRenderType.drawFromBuffer(...)` is the submit call that `RenderLayer.draw(BuiltBuffer)`
  used to be.
* `RenderSystem.setShader`/`setShaderTexture`/`enableBlend`/`depthMask`/`viewport`/`colorMask`/
  `clear`/`enableScissor` — not present. State lives in the pipeline and the pass.
* `ShaderProgram`/`ShaderInstance`, `VertexBuffer`/`VertexArray`/VAOs, `Tesselator`/`Tessellator`
  immediate mode, `GlStateManager` (now GL-backend-only under `com.mojang.blaze3d.opengl`),
  `MinecraftClient.framebuffer`, `WindowFramebuffer`.
* `Minecraft` has no `getMainRenderTarget()`; the main target is `GameRenderer.mainRenderTarget()`,
  and the supported way to redirect the main pass is the public
  `RenderSystem.outputColorTextureOverride` / `outputDepthTextureOverride`.

**No replacement at all** — these are the real design costs:

| 1.21.11 capability BBS uses | 26.2 status |
|---|---|
| Stencil test / write / ref | **Not available — but this is not a 26.2 regression, and it is not what BBS uses.** `DepthStencilState` is a record of `(CompareOp depthTest, boolean writeDepth, float depthBiasScaleFactor, float depthBiasConstant)`, `VulkanRenderPipeline` never programs `VkStencilOpState`, and `GlStateManager` has no `_stencil*` entry points. `grep -i stencil` over the whole 1.21.11 client jar returns **zero** hits, so 1.21.11's API had no stencil either; stencil-capable formats (`D24_UNORM_S8_UINT`, `S8_UINT`) exist only as textures. BBS's `StencilFormFramebuffer` is legacy naming — it renders into a colour attachment and reads one pixel back (§5.4). What actually breaks is the raw read-back, not a stencil test. |
| MRT via `glDrawBuffers` | Declared by the pass descriptor's attachment list (one `withColorAttachment` per target) plus the pipeline's `withColorTargetState(index, …)`; `glDrawBuffers` itself is gone. |
| `glBlitFramebuffer` | Only `RenderTarget.blitAndBlendToTexture` on a vanilla target. A BBS-to-BBS blit must be a full-screen quad with a pipeline. |
| Synchronous read-back (`glReadPixels`, `glGetTexImage`) | Asynchronous: `CommandEncoder.copyTextureToBuffer(...)` + `onDone` callback + `GpuBuffer.map(true, false)`. The texture needs `USAGE_COPY_SRC`, the buffer `USAGE_COPY_DST`. Vanilla's `net.minecraft.client.Screenshot` is the reference implementation; `Texture.pixelsFromTexture` in this branch follows it. |
| Texture units (`glActiveTexture`/`glBindTexture`) | Samplers are bound by name per pass: `RenderPass.bindTexture("Sampler0", view, sampler)`. |
| `glGenerateMipmap` | No command. The chain has to be built on the CPU at upload time (vanilla has `net.minecraft.client.renderer.texture.MipmapGenerator`). |
| `glViewport` / `glDepthRange` / `glScissor` as global state | A pass is created with a `RenderPass.RenderArea`, and scissoring is `RenderPass.enableScissor/disableScissor`. |
| Compute shaders, storage buffers | **Not in Blaze3D 26.2** — no dispatch entry point, no `STORAGE` buffer usage. Anything BBS wanted on the GPU has to become a fragment pass. |
| Persistent mapping | Available (`StagingBuffer.PersistentlyMapped`, `DeviceFeatures.persistentMapping()`), which is what a per-frame UI batcher wants. |

### 3.2 The graphics core (`mchorse.bbs_mod.graphics.*`)

Rebuilt on the 26.2 device API, keeping the mod's own class and method names so that the call-site
migration is a rename rather than a redesign.

| File | Was | Is |

### 3.3 The draw sequence everything has to become

For reference while migrating call sites, the canonical 26.2 immediate draw — extracted from the
bytecode of `net.minecraft.client.renderer.DebugCrosshairRenderer`:

```java
BufferBuilder builder = new BufferBuilder(
    ByteBufferBuilder.exactlySized(vertexFormat.getVertexSize() * vertexCount),
    PrimitiveTopology.TRIANGLES,
    vertexFormat);

builder.addVertex(x, y, z).setColor(argb).setNormal(nx, ny, nz).setUv(u, v);   // …per vertex
MeshData mesh = builder.buildOrThrow();

GpuBuffer vertices = RenderSystem.getDevice().createBuffer(
    () -> "bbs geometry", GpuBuffer.USAGE_VERTEX, mesh.vertexBuffer());
mesh.close();

RenderSystem.AutoStorageIndexBuffer indices = RenderSystem.getSequentialBuffer(PrimitiveTopology.TRIANGLES);
GpuBufferSlice transforms = RenderSystem.getDynamicUniforms()
    .writeTransform(modelViewMatrix, colorModulator, modelOffset, textureMatrix);

RenderPass pass = RenderSystem.getDevice().createCommandEncoder().createRenderPass(
    () -> "bbs pass",
    colorTextureView,      // or RenderSystem.outputColorTextureOverride to draw into the main target
    Optional.empty(),      // no clear
    depthTextureView,      // nullable
    OptionalDouble.empty());

RenderSystem.bindDefaultUniforms(pass);              // Projection / Fog / Globals …
pass.setPipeline(pipeline);
pass.setUniform("DynamicTransforms", transforms);    // BBS's own per-draw block
pass.bindTexture("Sampler0", texture.view(), texture.sampler());
pass.setVertexBuffer(0, vertices.slice());
pass.setIndexBuffer(indices.getBuffer(indexCount), indices.type());
pass.drawIndexed(0, 0, 0, indexCount, 1);
pass.close();                                        // submits the pass
```

Three things worth noting, because they are where a naive migration goes wrong: the index buffer
for non-indexed geometry comes from `RenderSystem.getSequentialBuffer`, `bindDefaultUniforms` is
what supplies `Projection`, and the pass is only submitted when it is closed.

### 3.4 The immediate-geometry primitive the batchers rebuild on

`graphics/gpu/BBSGeometryQueue.java` wraps vanilla's `StagedVertexBuffer` — the same staging ring the
world renderer batches its extracted geometry with — so that the two places BBS builds geometry by
hand have a 26.2-shaped home: `Batcher2D` (the whole 2D interface) and `Draw` (the 3D gizmos,
wireframes and arcs).

Its lifecycle is forced by the API, not chosen: vertices are written into a batch
(`begin(format, topology)` → `VertexConsumer`), the batch is pushed to the GPU by `upload()`, and
`upload()` **cannot** run while a pass is open, because 26.2's encoder rejects any command issued
between a pass opening and closing. So a frame is necessarily "build everything (no pass open) →
upload → open a pass → submit each batch → close", where the 1.21.11 code could interleave building
and drawing freely through the `Tessellator`. That ordering constraint is the single most
consequential difference for the interface code.

## 4. The rename: done, and what it bought

**Done.** `tools/rename/RenameYarnToOfficial.java` renamed the sources from Yarn to official names:
363 files changed, 5,805 identifiers, no structural change, comments and formatting byte-identical
(the tool splices by source range rather than reprinting). `docs/research/rename-run-report.txt` has
the run's own statistics.

Three things had to be right for it to be trustworthy, and each was found by it producing a
half-renamed tree first:

1. **The parser's language level.** JavaParser does not inject the symbol resolver into a
   compilation unit it cannot fully parse at the configured level. On the default level the mod's
   Java 21 syntax failed to parse in most files, every resolution then failed with *"Symbol
   resolution not configured"*, and the tool quietly changed 358 of 1,590 files.
2. **Type names in expression position.** `Identifier.of(…)`, `MinecraftClient.getInstance()`,
   `RotationAxis.POSITIVE_X` are `NameExpr` nodes, not `ClassOrInterfaceType`, so the type walk
   never sees them. Renaming the imports and leaving the bodies saying `RotationAxis.…` does not
   compile.
3. **`Node.equals` is structural.** Three occurrences of the same identifier in one file are
   "equal", so a `Map<Node, String>` keeps one and renames one. Edits are keyed by source range
   instead — and the dedupe set has to be cleared per file, because two files routinely have an
   import at the same line and column.

An override is the one case where a missed rename compiles and is still wrong — a method that keeps
its Yarn name silently stops overriding — so declarations carrying `@Override` that match an
inherited Minecraft method by name and arity are renamed too (108 of them).

**What it bought.** The compile error profile changes shape, which is the whole point:

| | before the rename | after |
|---|---|---|
| first errors javac reports | `程序包 net.minecraft.client.gl 不存在`, `net.minecraft.entity 不存在`, … — every Yarn package, nothing about the API | 544 errors that are real 1.21.11→26.2 deltas |
| dominant category | package resolution | 262 missing symbols (49 distinct: `getEntityWorld` ×38, `PacketByteBufs` ×38, `id` ×22, `getEntityPos` ×16, `getEquippedStack` ×12, …) |
| second | — | 54 × `ItemStack.copyFrom` signature change, 30 × float→int conversion losses, `Entity.getViewXRot/getViewYRot`, `Vec3.atLowerCornerWithOffset`, `StateHolder.getValueOrElse`, `Level.setBlockAndUpdate` |
| access | — | `LivingEntity.useItem`, `useItemRemaining`, `autoSpinAttackTicks`, `setLivingEntityFlag` are `protected` in 26.2 — these are the access-widener entries, now with their real targets |
| Fabric API | — | `net.fabricmc.fabric.api.itemgroup.v1`, `PacketByteBufs` |

Two caveats that belong to the follow-up rather than to the rename:

* **Mixin annotation strings were not touched**, deliberately. `@Inject(method = "render(Lnet/minecraft/client/util/math/MatrixStack;…)V")` and `@At(target = …)` hold yarn descriptors as *strings*; they need 26.2's descriptors, which is port work, not renaming.
* Three files ended up with two imports of the same simple name and were fixed by fully qualifying the Minecraft type (`Axis` → `com.mojang.math.Axis` in `Draw`/`GizmoPie`, `AABB` → `net.minecraft.world.phys.AABB` in `UIModelBlockPanel`). The tool reports these; it does not silently pick one.

### 5.1 GL call → 26.2 replacement

| 1.21.11 call | 26.2 |
|---|---|
| `glGenTextures` / `glDeleteTextures` | `GpuDevice.createTexture(...)` / `GpuTexture.close()` — done, `Texture` |
| `glTexImage2D` / `glTexSubImage2D` | `CommandEncoder.writeToTexture(tex, buf, mipLevel, depthOrLayer, x, y, w, h)` + `CommandEncoder.submit()` — done |
| `glTexParameteri(GL_TEXTURE_*)` | `GpuSampler` at bind time — done, `TextureFilter` |
| `glGetTexImage` / `glReadPixels` | `copyTextureToBuffer` + `onDone` + `GpuBuffer.map(true, false)` — done |
| `glGenerateMipmap` | CPU `MipmapGenerator` at upload time |
| `glGenFramebuffers` / `glBindFramebuffer` | `RenderPassDescriptor` + `CommandEncoder.createRenderPass` — done |
| `glFramebufferTexture2D` / `glFramebufferRenderbuffer` | `RenderPassDescriptor.withColorAttachment` / `withDepthAttachment` — done |
| `glDrawBuffers` | attachment list + `RenderPipeline.Builder.withColorTargetState(index, …)` |
| `glClear` / `glClearBufferfv` | clear values in the pass descriptor, or `CommandEncoder.clearColorAndDepthTextures` outside a pass — done |
| `glViewport` | `RenderPass.RenderArea` |
| `glScissor` | `RenderPass.enableScissor(x, y, w, h)` |
| `glEnable(GL_BLEND)` + `glBlendFunc` | `ColorTargetState(BlendFunction.…)` on the pipeline |
| `glDepthFunc` / `glDepthMask` | `DepthStencilState(CompareOp.…, writeDepth)` |

### 5.3 Interface rendering

`Batcher2D` (863 lines) and the `UIRenderer` family draw the entire BBS interface through
`BufferBuilder` + `RenderLayer` + `RenderSystem` state. In 26.2:

* geometry goes into a `BufferBuilder` on `DefaultVertexFormat.POSITION_TEX_COLOR`, is finished into
  `MeshData`, and is submitted through a `RenderType`/`PreparedRenderType`;
* per-draw transforms and the colour modulator come from `RenderSystem.getDynamicUniforms().writeTransform(modelView, color, offset, textureMatrix)`, set as the `"DynamicTransforms"` uniform;
* the projection comes from `RenderSystem.getProjectionMatrixBuffer()`;
* BBS's own pixel-art/selection/subtitle shaders keep their GLSL and their std140 blocks, and get
  pipelines from `BBSRenderPipelines`.

The `DrawContext` → `GuiGraphicsExtractor`/`GuiRenderer` change affects the five files that draw
through vanilla's interface API rather than BBS's own batcher. BBS's editor screens are mostly
custom-drawn, so the bulk of the work is the batcher, not vanilla's extractor — but where vanilla's
interface API *is* used, the names all move, and the moves are not guessable from the old ones:

| 1.21.11 (Yarn) | 26.2 |
|---|---|
| `GuiGraphics#drawTexture` | `blit` (all four overloads survive, plus a new `blit(GpuTextureView, GpuSampler, …)`) |
| `drawGuiTexture` | `blitSprite` |
| `drawTexturedQuad` | `blit` / `innerBlit` |
| `drawString` / `drawCenteredString` | `text` / `centeredText` |
| `renderItem` / `renderTooltip` | `item` / `tooltip` |
| `Screen#render` / `renderBackground` | `extractRenderState` / `extractBackground` |
| `ClickableWidget#renderWidget` | `extractWidgetRenderState` |
| `FontStorage` | `FontSet` |
| `resources.model.Material` | `resources.model.sprite.Material` (and `SpriteId` is new) |
| `world.inventory.ClickType` | `ContainerInput` |
| `gui.render.state.*` | `renderer.state.gui.*` (whole package) |

`GuiSignRenderer` and `GuiSignRenderState` are removed outright, and
`AbstractWidget`'s `x`/`y` are private now, so a widget that positioned itself by writing them needs
accessors or a mixin. `net.minecraft.client.gui.navigation.*` and `layouts.LayoutElement` are
unchanged, so BBS's own layout code ports as-is.

The same research also settled two things this document had left open or got wrong: yarn's
`DrawContext#drawTexture` does exist in 1.21.11 (it has no *official* member of that name — the
official one is `blit`), and post-processing is the one surface that carried over untouched.

### 5.4 Cursor picking reads back one pixel

`StencilFormFramebuffer` (+ `FilmStencilPicker` above it, + the pickable-form path) answers "which
form, which bone is under the cursor". Despite the name there is no stencil buffer in it: it draws
the forms into a colour attachment with the `picker_*` shaders, then binds a private read
framebuffer to that colour texture and calls `glReadPixels(x, y, 1, 1, GL_RGBA, GL_FLOAT, …)` —
one pixel, synchronously, twice (there is a small rect read for the multi-pixel variant).

That is the part Vulkan breaks: **there is no `glReadPixels` and no GL context at all when the
Vulkan backend is active.** The replacement already exists in this branch —
`Texture.pixelsFromTexture`, which follows vanilla's own screenshot recipe
(`copyTextureToBuffer` + a completion callback + `GpuBuffer.map(true, false)`), and which can copy a
one-pixel region as easily as a full frame.

So the work is smaller than it looked: point the two read sites at the new read-back, delete the
private read FBO and the `GlTexture` id cast, and confirm the resulting colour is the same value
the float read produced. The picker *shaders* need no change — writing an index into a colour
attachment is exactly what 26.2 wants.

`Texture.readRegion(x, y, w, h)` and `Texture.readPixel(x, y)` in this branch are exactly that:
the region form of `copyTextureToBuffer`, which is the same call as the full read with a smaller
box, returning the values as normalized floats so the comparison at the call site is unchanged.
Note the Y convention flips — 26.2 counts texels from the top-left, `glReadPixels` counted from the
bottom.

### 5.5 The supported way to draw custom geometry inside the world frame

`MultiBufferSource`, `Tesselator` and `ItemRenderer` are gone in 26.2, so the entity/model side of
BBS cannot keep building `VertexConsumer`s against a buffer source. The entry point that replaces it
is `SubmitNodeCollector.submitCustomGeometry(PoseStack, RenderType, CustomGeometryRenderer)`, which
routes the draw to the outline, translucent or solid batch according to the `RenderType` — and items
go through `ItemModelResolver` + `ItemStackRenderState` + `submitItem(...)`. That is the shape the
form renderers (`MobFormRenderer`, `ModelFormRenderer`, `ItemFormRenderer`) have to take: build the
geometry inside a `CustomGeometryRenderer` callback instead of returning a consumer.

### 5.6 Mixins

53 mixins target engine internals. The ones that touch rendering
(`WorldRendererMixin`, `GameRendererMixin`, `RenderLayerMixin`, `EntityRenderDispatcherMixin`,
`LivingEntityRendererMixin`, `ModelPartMixin`, `WindowMixin`, …) have to be re-pointed at 26.2's
`LevelRenderer`, `GameRenderer` (whose frame is now a frame graph of passes), the
`rendertype`/`feature` extraction pipeline and the new render-state records. This is where the
"verify at runtime" cost concentrates, because a mixin that fails to apply is a silent behavioural
change until something renders wrong.

### 5.7 Data and gameplay APIs

Not a rendering topic, but the same rename applies: `Identifier` → `net.minecraft.resources.Identifier`,
`ItemStack` components, `Registries`, `Text`, `PlayerLikeEntity` (already renamed once on this
branch), `TrackedData`. The 1.21.11 branch's access widener entries show which internals BBS leans
on; each needs its 26.2 counterpart before the mixins compile.

### 5.8 Sodium / Iris

* **Sodium** rewrote its renderer onto Blaze3D for 26.2 and added native Vulkan support in 0.9.0
  ("the first version to experimentally support Vulkan", reachable from the Graphics API option);
  0.9.2 is current for 26.2. So BBS's `utils/sodium` and the sodium mixins are re-portable.
* **Iris** publishes for 26.2 (`1.11.4+26.2`) but its changelog states plainly that **Vulkan is not
  supported**. BBS's Iris integration (`utils/iris`, `BBSRendering.assignIrisPipeline`, the PBR
  texture wrappers) is therefore a *reduced* port: keep it working on the OpenGL backend and detect
  and disable it on Vulkan rather than assuming parity. Iris's Vulkan story is reported to be a
  separate loader, which is rumour rather than a released artifact.
* **Distant Horizons** ships a 26.2 build with an explicit rendering-engine option (Auto/OpenGL/
  Blaze3D) and warns when OpenGL is used. **Embeddium** and **Indium** have no 26.x builds and are
  effectively abandoned; Sodium now ships NeoForge builds itself.

### 5.9 Mixin selector strings: the port that the rename could not do

§4 records that mixin annotation strings were deliberately left alone, because they hold Yarn
descriptors as *strings* and no rename tool can see them. §6.3 repeats the warning. This is what that
warning costs, measured: **every one of the fourteen `bbs.mixins.json` mixins carried at least one
dead selector, and the first two to be applied killed the client before the main menu.**

The failure is not a silent behavioural change - `bbs.mixins.json` and `bbs.client.mixins.json` are
`required: true` with `defaultRequire: 1`, so one unresolvable selector aborts class transformation
and the game dies with `Mixin transformation of … failed`. There is also no refmap to fall back on:
26.2 ships unobfuscated, so Loom writes no refmap and Mixin matches these strings literally against
official names.

Symptom seen at startup (the reported crash):

```
Mixin apply for mod bbs failed bbs.mixins.json:EntityInvoker  -> net.minecraft.world.entity.Entity
  InvalidAccessorException: No candidates were found matching setFlag(IZ)V
Mixin apply for mod bbs failed bbs.mixins.json:LivingEntityMixin -> net.minecraft.world.entity.LivingEntity
  InvalidInjectionException: @Inject on onApplyDamage could not find any targets matching 'applyDamage'
Minecraft has crashed! -> Mixin transformation of net.minecraft.world.entity.LivingEntity failed
```

The stale names were of three kinds, and only the first is a plain rename:

1. **Renamed members** - `setFlag` → `setSharedFlag`, `applyDamage` → `hurtServer`,
   `getBaseDimensions` → `getDefaultDimensions`, `dropItem` → `drop`, `setBlockBreakingInfo` →
   `destroyBlockProgress`, `spawnEntity` → `addFreshEntity`, `useOnBlock` → `useOn`,
   `writeCustomData`/`readCustomData` → `addAdditionalSaveData`/`readAdditionalSaveData`.
2. **Reshaped signatures** - `hurtServer` returns `boolean` where `applyDamage` returned `void`, so
   the callback had to become `CallbackInfoReturnable<Boolean>`; `BlockItem.place` takes
   `BlockPlaceContext` and returns `InteractionResult` (not a `BlockState`-carrying `boolean`); the
   accessor fields moved (`glidingTicks` → `fallFlyTicks`, `lastSpeed` → `speedOld`,
   `animationProgress` → `position`, PrimaryLevelData's `levelInfo` → `settings`).
3. **Selectors that were never Yarn-to-official renames at all** - `ServerPlayNetworkHandlerMixin`
   still targeted `parse` and `onPlayerInteractBlock`, and its `@Redirect` pointed at
   `ServerPlayerInteractionManager#interactBlock`; 26.2 has `parseCommand`, `handleUseItemOn` and
   `ServerPlayerGameMode#useItemOn`. `BlockItemMixin`'s descriptor was a full Yarn string.

Two traps are worth recording, because both survive a naive "does the member exist?" check:

* **A selector resolves against the target class only, not its supertypes.** `PlayerLikeEntityMixin`
  injects into `Avatar#getDimensions`, which compiles and "exists" through inheritance, but `Avatar`
  does not declare it - `getDimensions` lives on `Entity`/`LivingEntity`, and what `Avatar`
  overrides is `getDefaultDimensions`. Mixin rejects it at APPLY.
* **A selector can be a `static final String` constant.** `WorldChunkMixin` builds its target from
  `SET_BLOCK_STATE`, so the Yarn descriptor was invisible to both the rename tool and to any audit
  that only reads annotation literals - and it still failed the whole main config.

`gradlew mixinAudit` (backed by `tools/mixin-audit/audit.py`) checks all of this offline against the
resolved 26.2 jar, and `check` and `build` now depend on it. It validates `@Mixin`
targets, every `@Inject`/`@Redirect`/`@ModifyArg`/`@ModifyVariable`/`@WrapOperation`/`@ModifyConstant`
selector (including selectors named by a constant), nested `@At` targets, `@Accessor`/`@Invoker`
members and `@Shadow` members. It reports **0 problems** across the 14 main mixins and the 43 non-Iris
client mixins as of this port; the 10 `bbs.iris.mixins.json` targets report as missing, which is the
expected and intended result when Iris is not installed (§5.8).

Verification used the real loader rather than only the static check: launching with the rebuilt jar
reaches `MixinExtras` initialization, applies every BBS mixin, and gets as far as the mod's own
client entrypoint with `Mixin apply for mod bbs failed` = **0** (it was 2 in the reported crash log).
The preflight log is kept at `docs/research/26.2-mixin-preflight-2026-10-03.log`.

### 5.10 Two startup bugs that were hidden behind the mixin crash

With the mixins applying, the client gets much further and hits two more 26.2 changes. Both are
verified by running the client, not inferred.

**The form palette cannot be built during client initialization.** `ExtraFormSection` puts a default
`ItemStack` into its item form, and 26.2 made item components registered data, so
`ItemStack(Holder, int)` reads the holder's component map. Vanilla binds those maps only when the
client takes the server's registries (`RegistryDataCollector.collectGameRegistries`, reached from
`ClientConfigurationPacketListenerImpl.handleConfigurationFinished`). Measured: constructing an
`ItemStack` throws `NullPointerException: Components not bound yet` at `onInitializeClient`, at
`CLIENT_STARTED`, **and** on the first client tick — it is not a race that can be waited out, only a
world join satisfies it.

So `BBSResources.init()` moved to `ClientPlayConnectionEvents.JOIN`, and `FormCategories` gained
`ensureInitialized()` (idempotent, with the flag raised *before* the sections are initiated so a
section reaching back for the palette cannot recurse). The resource-pack reload listener was calling
`setup()` unconditionally and had to be gated on the palette having been built at least once: that
listener runs during startup, its existing `cemSourcePack == null` guard does not stop the first
call (the listener is what sets that field), and an unguarded `setup()` there takes the whole
resource reload down with it — the log says `Caught error loading resourcepacks, removing all
selected resourcepacks`. Rebuilding before the first build is also pointless: the first build happens
at the join and already sees the current pack state.

**`Entity#getId()` now throws while the id is unassigned.** 26.2 throws
`IllegalStateException("Tried to access entity ID before ID assignment")` until the entity is added
to a level. `ClientPlayerEntityFilmSneakMixin` called it from `isShiftKeyDown`/`isCrouching`, which
the render path reaches with a local player that is not in any level yet —
`Minecraft.renderFrame` → `LocalPlayer.raycastHitResult` → `isShiftKeyDown` — so the game died on the
main menu (`Description: Render Frame`). The mixin now reads the raw `id` field through the access
widener and treats `INVALID_ENTITY_ID` as "no film pose"; asking `getId()` was never the right
question, since a pose can only be looked up for an entity that has an id. A `@Shadow` field cannot
be used for this: `id` is declared on `Entity` and Mixin resolves shadowed members against the target
class, so it fails at APPLY with "was not located in the target class LocalPlayer".

After both fixes the client reaches the title screen, joins a world, and builds the palette exactly
at the join (`FormCategories.setup` ← `ensureInitialized` ← `BBSResources.init` ← `ClientPlayConnectionEvents.JOIN`),
with no "Components not bound yet" and no resource-pack reload failure anywhere in the log.

### 5.11 Confirmed next blocker: RGB8 cannot be a 26.2 texture

Past that point the first world frame dies in BBS's own snapshot texture — the open question §7
listed as "which `GpuFormat`s are guaranteed to be usable" now has a measured answer for this one:

```
java.lang.IllegalArgumentException: RGB8_UNORM format cannot be used to create textures
  at com.mojang.blaze3d.opengl.GlDevice.createTexture(GlDevice.java:177)
  at mchorse.bbs_mod.graphics.texture.Texture.allocate(Texture.java:288)
  at mchorse.bbs_mod.client.BBSRendering.captureAndRestore(BBSRendering.java:768)
```

`GlDevice.createTexture` throws when `GlConst`'s internal/external/type triple for the format is not
a usable combination, and `RGB8_UNORM` is one of those. The snapshot texture is deliberately RGB —
`BBSRendering.getTexture()` says why: the world framebuffer's cleared sky carries a non-opaque alpha
that, if preserved, shows through as the panel background in the preview blit, because
`GUI_TEXTURED` multiplies texel alpha. So the fix is not a one-line format swap: an RGBA8 snapshot
has to have its alpha dropped at capture time instead. Until that is done, anything that calls
`BBSRendering.getTexture()` (panel preview, video export) takes the client down on its first frame.
This is BBS render work, not a port slip, and it needs a real visual check.

### 6.1 What the port could not do mechanically

Three classes of change needed judgement rather than substitution, and they are the places to look
first at runtime:

* **Immediate geometry has no cached buffer any more.** `Tesselator` is gone, so
  `Draw`, `Gizmo`, `ScreenQuadPass`, `BBSPickerRenderer`, `MotionPath` and `CustomVertexConsumerProvider`
  now build a `BufferBuilder`, upload a `GpuBuffer`, draw through `PreparedRenderType.drawFromBuffer`
  and close it — one allocation per batch where 1.21.11 reused a ring. `BBSGeometryQueue` exists in
  the repo for the case where that shows up in a profile, and several files carry private copies of
  the same `flush` helper that should be promoted to one public one.
* **The extraction/submit split moved work across frames.** Name tags go through
  `SubmitNodeCollector.submitText`, the breaking overlay through `submitCustomGeometry`, and the
  form preview through the picture-in-picture path. Each is a faithful translation of the same draw,
  but the timing changed, so each needs one visual check.
* **Two renamer artefacts had to be recognised before they could be fixed.** A one-arg
  `PoseStack.rotateAround` was yarn `multiply` (45 sites became `mulPose`, no pivot invented), and
  `setUv1`/`setUv2` were yarn `setOverlay`/`setLight`. `tools/mappings/*-members.tsv` plus
  `git show origin/1.21.11:<file>` is what settles this class of question; a name-only view of the
  diff cannot.

### 6.2 Known GL-backend-only paths

These compile and work on `Graphics API = Prefer OpenGL`. They hard-cast `GpuTexture` to
`com.mojang.blaze3d.opengl.GlTexture` or call raw GL, so **they will fail on the Vulkan backend**
until ported. Each site carries a TODO naming the replacement:

| Path | Sites | Replacement |
|---|---|---|
| Screenshot / video export texture ids | `ScreenshotRecorder`, `WorldVideoExportSession`, `UIFilmRecorder`, `UIFilmPreview`, `FilmQueueExporter`, `UIUnifiedPickOverlayPanel` | `Texture.pixelsFromTexture(Texture)` / `Texture.readRegion(...)`, which already exist |
| Cursor picking | `StencilFormFramebuffer.getHighlightGlId` + its `glReadPixels` | `Texture.readPixel(x, y)` (§5.4) |
| Form preview / screen probe | `FormFramebuffer.getIdentifier`, `ModelPreviewRenderer.getColorGlId`, `ScreenPixelProbe` | the `blit(GpuTextureView, GpuSampler, …)` route or `pixelsFromTexture` |
| Zero-copy texture adoption | `AdoptedTexture`'s `GlTexture` subclasses | no 26.2 equivalent; it is a GL-only optimisation |
| Iris blend repair | `FramebufferFormRenderer` | needs a 26.2-state equivalent, or a Vulkan guard |

### 6.3 Decisions that need a product answer, not a compiler

* **`SpecialModelRenderer#submit` lost its `ItemDisplayContext`** — 26.2 does not pass it because
  vanilla doesn't need it, but BBS resolves a different form per context. It is now captured by
  `SpecialModelWrapperMixin` at the head of `SpecialModelWrapper#update`; confirm in game that the
  GUI/first-person variants come back.
* **`fabric.mod.json` now declares `~26.2` and Java 25.** If the mod should keep loading on 1.21.11
  from the same jar, that is not possible — this branch is 26.2-only.
* **The Iris mixins moved to their own `required: false` config.** With Iris absent they are skipped
  instead of failing the load; with Iris present they apply. Iris still does not support Vulkan, so
  a shaderpack on the Vulkan backend is unsupported regardless.
* **`BEFORE_ENTITIES` → `COLLECT_SUBMITS`** and `AFTER_ENTITIES` → `AFTER_SOLID_FEATURES`: the 26.2
  event set has no exact counterparts, and these bracket the same draw.
* **HUD drawing now goes through `HudElementRegistry.addLast`**, which renders unconditionally like
  the old callback. If F1 should hide the BBS overlay, the attachment point has to change.
* **`BakedStructure` seeds `tesselateBlock` with `state.getSeed(pos)`**, which is a deliberate
  behaviour fix rather than a translation — confirm the block-model previews still look right.
* **`RenderLayerMixin` was deleted** (26.2 has no `RenderType.draw`); its two jobs live in
  `CustomVertexConsumerProvider`. The related mixin target strings across all 53 mixin files were
  re-pointed, but a mixin that silently fails to apply is invisible until something renders wrong,
  so a launch with `-Dmixin.debug.export=true` (or simply watching the log) is worth one pass.

## 7. Open questions

* **26.3 moved the GPU API again.** 26.3 introduces a `com.mojang.renderpearl` namespace
  (`api.{buffers,commands,device,pipeline,textures,vertex}`, `backend.{opengl,vulkan,common,util}`,
  `frontend.shaders`) with `GpuBuffer` becoming an interface, leaving the Minecraft-facing pieces in
  `blaze3d`. 26.2 code and 26.3 documentation must not be mixed; a 26.3 branch is a second
  migration, not a version bump.
* **`GpuFormat` support matrix.** Which `GpuFormat`s are guaranteed to be usable as colour
  attachments on the Vulkan backend (`RGB8_UNORM` in particular) needs a runtime check via
  `DeviceLimits.maxTextureSizeForFormat` or a failed pipeline compile.
* **Post-processing is the one surface that did not change.** 26.2's `post_effect/*.json` files are
  byte-identical to 1.21.11's, `PostChainConfig` is unchanged, and there is no registry — a mod ships
  `assets/<ns>/post_effect/*.json` and calls `ShaderManager.getPostChain(id, targets)`
  (`GameRenderer.setPostEffect` is private). The only addition is a `Projection`/`ProjectionMatrixBuffer`
  parameter on `PostChain.load`. BBS's `assets/bbs/shaders/post/box_blur_opaque.fsh` should therefore
  carry over unchanged.
* **`DeviceLimits.minUniformOffsetAlignment`** vs the uniform ring buffer BBS will want for its
  per-draw blocks — the vanilla `DynamicUniforms` storage already handles it, but a BBS-owned one
  would have to.
* **Runtime behaviour of the remaining raw GL.** No GL context is expected while the Vulkan backend
  is active, but that is inferred from how each backend creates its window rather than observed. The
  first Vulkan test run should assert it.

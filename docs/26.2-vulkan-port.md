# Porting BBS mod to Minecraft 26.2's GPU abstraction

This document is the working reference for the `26.2` branch. It records what Minecraft 26.2
actually is, what the port has already done, what every remaining OpenGL touchpoint in the mod has
to become, and in what order.

Everything marked **verified** below was checked against the real artifacts on this machine (the
unobfuscated 26.2 client jar, its version manifest, the Fabric metadata and the Fabric API jar), not
recalled from memory. Where a claim comes from an external source it is linked; where it is still
open it is listed under *Open questions* at the end.

## 2. What 26.2 changes for a mod like BBS

### 2.1 Minecraft ships unobfuscated, and there are no mappings any more

**Verified.** `~/.gradle/caches/fabric-loom/26.2/minecraft-client.jar` (the raw Mojang download)
contains `net/minecraft/client/Minecraft.class`, and none of its 10,952 classes has an obfuscated
name. The 26.2 version JSON has no `client_mappings` download at all.

Fabric's side matches:

* `net.fabricmc:yarn` stops at `1.21.11+build.6` (maven metadata `<release>`); there is no 26.x Yarn.
* `meta.fabricmc.net/v2/versions/loader/26.2` reports intermediary `0.0.0` — the identity mapping.
* Loom therefore runs with `fabric.loom.disableObfuscation=true`, takes no `mappings` dependency, and
  neither remaps the game nor the mod's own classes.

Two consequences that decide the whole port:

1. **A mod for 26.2 compiles against Mojang's own names**, so every Minecraft reference in BBS's
   1,566 source files has to move from Yarn to official names. That is mechanical but it is the
   gate: until it is done, `compileClientJava` reports "package net.minecraft.client.gl does not
   exist" for every file at once and says nothing about the real API deltas. §4 is about this.
2. **Fabric API is a plain `implementation` dependency** (`implementation "net.fabricmc.fabric-api:fabric-api:0.153.0+26.2"`),
   not `modImplementation`, and the same for the loader — there is no remapping step that a
   mod-flavoured configuration could feed.

### 2.2 The rendering backend: Vulkan exists, OpenGL is still the default in 26.2

From the 26.2 release notes and the Fabric developer documentation (external, see links at the end):

* Video Settings exposes **Graphics API: `Default` | `Prefer Vulkan (Experimental)` | `Prefer OpenGL`**,
  backed by `net.minecraft.client.PreferredGraphicsApi`. In 26.2, `Default` means **OpenGL**; the
  first 26.2 snapshot defaulted to Vulkan and the release moved it back.
* Vulkan requires Vulkan 1.2 plus `VK_KHR_dynamic_rendering` and push descriptors; macOS goes
  through MoltenVK. OpenGL is slated for removal in a later drop.
* Fabric's guidance is explicit that **raw OpenGL is not supported**: a mod has to render through
  Blaze3D. Vanilla's own GL calls are confined to `com.mojang.blaze3d.opengl.*`.

For BBS this has one important practical reading: **the port is not "write Vulkan code", it is
"stop writing OpenGL code"**. Everything in §5 goes through the backend-neutral device API, and the
same code then runs on both backends. A mod that reaches for `GL11` keeps working only while the
user has not switched to Vulkan.

> Testing note: `runClient --args="--graphicsBackend VULKAN"` is what the Caustica 26.2 project uses
> in this workspace. The supported switch is the in-game Graphics API option; treat the launch
> argument as a development convenience and confirm it in the log (`RenderSystem.getBackendDescription()`).

### 2.3 The modder-facing API is a small explicit RHI

**Verified** by `javap` over the 26.2 jar. The pieces BBS cares about:

| Area | Classes |
|---|---|
| Device | `com.mojang.blaze3d.systems.GpuDevice`, `GpuDeviceBackend`, `GpuBackend`, `DeviceInfo`, `DeviceFeatures`, `DeviceLimits`, `SamplerCache`, `RenderSystem.getDevice()` |
| Recording | `CommandEncoder` (+`CommandEncoderBackend`), `RenderPass` (+`RenderPassBackend`), `RenderPassDescriptor`, `RenderPass.RenderArea`, `TransientMemory`, `GpuFence` |
| Pipelines | `com.mojang.blaze3d.pipeline.{RenderPipeline, RenderPipeline.Builder, RenderPipeline.Snippet, CompiledRenderPipeline, BindGroupLayout, BindGroupLayout.Builder, ColorTargetState, DepthStencilState, BlendFunction, BlendEquation, RenderTarget, TextureTarget, MainTarget}` |
| Textures | `com.mojang.blaze3d.textures.{GpuTexture, GpuTextureView, GpuSampler, AddressMode, FilterMode}`, `com.mojang.blaze3d.GpuFormat` |
| Buffers | `com.mojang.blaze3d.buffers.{GpuBuffer, GpuBufferSlice, GpuFence, Std140Builder, Std140SizeCalculator}` |
| Vertex | `com.mojang.blaze3d.vertex.{VertexFormat, VertexFormat.Builder, DefaultVertexFormat, PoseStack, BufferBuilder, MeshData, StagingBuffer, ByteBufferBuilder}` |
| Frame graph | `com.mojang.blaze3d.framegraph.{FrameGraphBuilder, FramePass}` — the vanilla frame is a graph of passes, and `net.minecraft.client.renderer.LevelTargetBundle` / `PostChain` hang off it |
| Shaders | `com.mojang.blaze3d.shaders.{ShaderSource, ShaderType, UniformType}`, `net.minecraft.client.renderer.ShaderDefines`, GLSL assets under `assets/<ns>/shaders/core`, post effects under `assets/<ns>/post_effect/*.json` |

Two details that make the port tractable:

* **GLSL is still the authoring language.** 26.2 ships 61 core shaders as `#version 330` `.vsh`/`.fsh`
  files, and the Vulkan backend compiles them at runtime
  (`com.mojang.blaze3d.vulkan.glsl.GlslCompiler` → SPIR-V via `lwjgl-shaderc`, with
  `SpvUniformBuffer`/`SpvSampler` doing the reflection). BBS's `assets/bbs/shaders/core/*` do not
  have to be rewritten in another shading language — but their uniform declarations do have to
  match the pipeline's bind group layout exactly, because the backend reflects the compiled module
  and checks it.
* **Vanilla's bind groups are public and reusable.** `net.minecraft.client.renderer.BindGroupLayouts`
  exposes `DYNAMIC_TRANSFORMS`, `PROJECTION`, `MATRICES_PROJECTION`, `FOG`, `GLOBALS`, `LIGHTING`,
  `SAMPLER0`, `SAMPLER1`, `SAMPLER2`, `SAMPLER0_SAMPLER1_SAMPLER2`, … so a BBS shader can declare
  `layout(std140) uniform DynamicTransforms { … };` and `Sampler0` verbatim and compose its
  pipeline out of those objects. `RenderPipeline.Snippet` has a public canonical constructor, so
  mod-side snippets are possible too.

### 2.4 What no longer exists, and what that costs BBS

**Verified** against the jar:

* `net.minecraft.client.gui.GuiGraphics` (Yarn `DrawContext`) — **gone**. 26.2 extracts GUI draws
  (`GuiGraphicsExtractor`, `net.minecraft.client.gui.render.GuiRenderState`) and replays them
  (`GuiRenderer`, `TextureSetup`). Every BBS interface element that drew through `DrawContext` and
  every `Batcher2D` consumer sits on this.
* `net.minecraft.client.render.RenderLayer` / `RenderSetup` — replaced by
  `net.minecraft.client.renderer.rendertype.{RenderType, RenderTypes, PreparedRenderType}`;
  `PreparedRenderType.drawFromBuffer(...)` is the submit call that `RenderLayer.draw(BuiltBuffer)`
  used to be.
* `RenderSystem.setShader`/`setShaderTexture`/`enableBlend`/`depthMask`/`viewport`/`colorMask`/
  `clear`/`enableScissor` — not present. State lives in the pipeline and the pass.
* `ShaderProgram`/`ShaderInstance`, `VertexBuffer`/`VertexArray`/VAOs, `Tesselator`/`Tessellator`
  immediate mode, `GlStateManager` (now GL-backend-only under `com.mojang.blaze3d.opengl`),
  `MinecraftClient.framebuffer`, `WindowFramebuffer`.
* `Minecraft` has no `getMainRenderTarget()`; the main target is `GameRenderer.mainRenderTarget()`,
  and the supported way to redirect the main pass is the public
  `RenderSystem.outputColorTextureOverride` / `outputDepthTextureOverride`.

**No replacement at all** — these are the real design costs:

| 1.21.11 capability BBS uses | 26.2 status |
|---|---|
| Stencil test / write / ref (the whole `FilmStencilPicker`, `StencilFormFramebuffer`, pickable-form path) | **Gone.** `DepthStencilState` is a record of `(CompareOp depthTest, boolean writeDepth, float depthBiasScaleFactor, float depthBiasConstant)`; `DepthStencilState` has no stencil operation, and `VulkanRenderPipeline` never programs `VkStencilOpState`. Stencil-capable formats (`D24_UNORM_S8_UINT`, `S8_UINT`) exist, so the attachment can be created, but nothing can configure the test. The picking has to be re-architected as colour-index picking (the BBS picker shaders already write a target index into a colour attachment — that path survives; the stencil *mask* does not). |
| MRT via `glDrawBuffers` | Declared by the pass descriptor's attachment list (one `withColorAttachment` per target) plus the pipeline's `withColorTargetState(index, …)`; `glDrawBuffers` itself is gone. |
| `glBlitFramebuffer` | Only `RenderTarget.blitAndBlendToTexture` on a vanilla target. A BBS-to-BBS blit must be a full-screen quad with a pipeline. |
| Synchronous read-back (`glReadPixels`, `glGetTexImage`) | Asynchronous: `CommandEncoder.copyTextureToBuffer(...)` + `onDone` callback + `GpuBuffer.map(true, false)`. The texture needs `USAGE_COPY_SRC`, the buffer `USAGE_COPY_DST`. Vanilla's `net.minecraft.client.Screenshot` is the reference implementation; `Texture.pixelsFromTexture` in this branch follows it. |
| Texture units (`glActiveTexture`/`glBindTexture`) | Samplers are bound by name per pass: `RenderPass.bindTexture("Sampler0", view, sampler)`. |
| `glGenerateMipmap` | No command. The chain has to be built on the CPU at upload time (vanilla has `net.minecraft.client.renderer.texture.MipmapGenerator`). |
| `glViewport` / `glDepthRange` / `glScissor` as global state | A pass is created with a `RenderPass.RenderArea`, and scissoring is `RenderPass.enableScissor/disableScissor`. |
| Compute shaders, storage buffers | **Not in Blaze3D 26.2** — no dispatch entry point, no `STORAGE` buffer usage. Anything BBS wanted on the GPU has to become a fragment pass. |
| Persistent mapping | Available (`StagingBuffer.PersistentlyMapped`, `DeviceFeatures.persistentMapping()`), which is what a per-frame UI batcher wants. |

### 3.3 The draw sequence everything has to become

For reference while migrating call sites, the canonical 26.2 immediate draw — extracted from the
bytecode of `net.minecraft.client.renderer.DebugCrosshairRenderer`:

```java
BufferBuilder builder = new BufferBuilder(
    ByteBufferBuilder.exactlySized(vertexFormat.getVertexSize() * vertexCount),
    PrimitiveTopology.TRIANGLES,
    vertexFormat);

builder.addVertex(x, y, z).setColor(argb).setNormal(nx, ny, nz).setUv(u, v);   // …per vertex
MeshData mesh = builder.buildOrThrow();

GpuBuffer vertices = RenderSystem.getDevice().createBuffer(
    () -> "bbs geometry", GpuBuffer.USAGE_VERTEX, mesh.vertexBuffer());
mesh.close();

RenderSystem.AutoStorageIndexBuffer indices = RenderSystem.getSequentialBuffer(PrimitiveTopology.TRIANGLES);
GpuBufferSlice transforms = RenderSystem.getDynamicUniforms()
    .writeTransform(modelViewMatrix, colorModulator, modelOffset, textureMatrix);

RenderPass pass = RenderSystem.getDevice().createCommandEncoder().createRenderPass(
    () -> "bbs pass",
    colorTextureView,      // or RenderSystem.outputColorTextureOverride to draw into the main target
    Optional.empty(),      // no clear
    depthTextureView,      // nullable
    OptionalDouble.empty());

RenderSystem.bindDefaultUniforms(pass);              // Projection / Fog / Globals …
pass.setPipeline(pipeline);
pass.setUniform("DynamicTransforms", transforms);    // BBS's own per-draw block
pass.bindTexture("Sampler0", texture.view(), texture.sampler());
pass.setVertexBuffer(0, vertices.slice());
pass.setIndexBuffer(indices.getBuffer(indexCount), indices.type());
pass.drawIndexed(0, 0, 0, indexCount, 1);
pass.close();                                        // submits the pass
```

Three things worth noting, because they are where a naive migration goes wrong: the index buffer
for non-indexed geometry comes from `RenderSystem.getSequentialBuffer`, `bindDefaultUniforms` is
what supplies `Projection`, and the pass is only submitted when it is closed.

## 4. The gate: renaming Yarn identifiers to official ones

Nothing else can be verified until the source stops saying `MinecraftClient`, `Identifier`,
`RenderLayer`, `net.minecraft.client.gl.*`.

Both mapping sets exist for 1.21.11 and can be **joined on that version's obfuscated names**:

* Yarn: `net.fabricmc:yarn:1.21.11+build.6:v2` → `mappings/mappings.tiny` (`official intermediary named`).
* Mojang: 1.21.11's version JSON → `downloads.client_mappings.url` → ProGuard `client.txt`
  (`obf → official`).

Joining them yields a `yarn → official` table (classes directly on the obf name; members on
`owner + name + descriptor`). `tools/mappings/` contains a generator for that table plus the
generated TSVs; see `tools/mappings/README.md`.

**Two cautions, learned the hard way:**

1. **The join gets you to 1.21.11-official names, not to 26.2 names.** 1.21.11 was obfuscated, so
   the mapping must be built against the 1.21.11 obf names; 26.2 is not obfuscated and its names
   have moved on again since (six months and three drops: 26.1, 26.2, 26.3).
2. **A blind textual rename is not safe.** Renaming a class name is; renaming a *method* name is
   not, because the same identifier is usually also a method on BBS's own types (`render`, `update`,
   `copy`). The rename needs type information. The two workable routes are a JavaParser +
   symbol-solver pass over the 1.21.11 source with the Yarn-named game jar on the classpath
   (keeps the source and its comments), or compiling at 1.21.11, remapping the bytecode with
   TinyRemapper using the joined table, and decompiling (loses comments and formatting). This
   document assumes the first route.

Once the rename lands, `compileClientJava` becomes a usable instrument and the remaining work in §5
can be done against compiler errors instead of guesswork.

### 5.3 Interface rendering

`Batcher2D` (863 lines) and the `UIRenderer` family draw the entire BBS interface through
`BufferBuilder` + `RenderLayer` + `RenderSystem` state. In 26.2:

* geometry goes into a `BufferBuilder` on `DefaultVertexFormat.POSITION_TEX_COLOR`, is finished into
  `MeshData`, and is submitted through a `RenderType`/`PreparedRenderType`;
* per-draw transforms and the colour modulator come from `RenderSystem.getDynamicUniforms().writeTransform(modelView, color, offset, textureMatrix)`, set as the `"DynamicTransforms"` uniform;
* the projection comes from `RenderSystem.getProjectionMatrixBuffer()`;
* BBS's own pixel-art/selection/subtitle shaders keep their GLSL and their std140 blocks, and get
  pipelines from `BBSRenderPipelines`.

The `DrawContext` → `GuiGraphicsExtractor`/`GuiRenderer` change affects the five files that draw
through vanilla's interface API rather than BBS's own batcher. BBS's editor screens are mostly
custom-drawn, so the bulk of the work is the batcher, not vanilla's extractor.

### 5.4 Stencil-based picking (the one redesign)

`FilmStencilPicker` + `StencilFormFramebuffer` + the pickable-form path render a stencil mask,
then compare against it to select a form under the cursor. 26.2 cannot express that: the pipeline
has no stencil state.

The replacement is the colour-index path BBS already has — `BBSShaders.PICKER_*` write a target
index into a colour attachment, and `BBSPickerRenderer` reads it back. The work is to move the
*mask* semantics (write 1 where a form is drawn, test equality, clear) onto a dedicated integer-ish
colour attachment and a read-back, and to drop the depth-stencil format from
`StencilFormFramebuffer`. `Texture.pixelsFromTexture` already provides the read-back.

### 5.5 Mixins

53 mixins target engine internals. The ones that touch rendering
(`WorldRendererMixin`, `GameRendererMixin`, `RenderLayerMixin`, `EntityRenderDispatcherMixin`,
`LivingEntityRendererMixin`, `ModelPartMixin`, `WindowMixin`, …) have to be re-pointed at 26.2's
`LevelRenderer`, `GameRenderer` (whose frame is now a frame graph of passes), the
`rendertype`/`feature` extraction pipeline and the new render-state records. This is where the
"verify at runtime" cost concentrates, because a mixin that fails to apply is a silent behavioural
change until something renders wrong.

### 5.6 Data and gameplay APIs

Not a rendering topic, but the same rename applies: `Identifier` → `net.minecraft.resources.Identifier`,
`ItemStack` components, `Registries`, `Text`, `PlayerLikeEntity` (already renamed once on this
branch), `TrackedData`. The 1.21.11 branch's access widener entries show which internals BBS leans
on; each needs its 26.2 counterpart before the mixins compile.

### 5.7 Sodium / Iris

* **Sodium** publishes `mc26.2-0.9.2` for Fabric and NeoForge with experimental Vulkan support, on
  top of Blaze3D. BBS's `utils/sodium` and the sodium mixins should be re-portable.
* **Iris** publishes `1.11.4+26.2` but its changelog states Vulkan is **not** supported there. BBS's
  Iris integration (`utils/iris`, `BBSRendering.assignIrisPipeline`, the PBR texture wrappers) is
  therefore a *reduced* port: keep it working on the OpenGL backend and detect and disable it on
  Vulkan rather than assuming parity.

## 6. Plan

| Phase | Work | Done when |
|---|---|---|
| 0 | Build scaffold, graphics core, probe (**done**) | `tools/26.2-api-probe.sh` green |
| 1 | Yarn→official rename tooling + rename of the whole source (**the gate**) | `./gradlew compileClientJava` runs and its errors are about behaviour, not name resolution |
| 2 | Core API deltas: `Identifier`, registries, components, client entry points, `Minecraft`/`GameRenderer`/`Window` | the non-render source set compiles |
| 3 | Render core migration: `RenderSystem`/`RenderLayer`/`BufferBuilder` call sites, `Batcher2D`, `Draw`, `BBSShaders` → `BBSRenderPipelines` | the client compiles; interface renders on both backends |
| 4 | Framebuffer/render-target call sites on the new `Framebuffer` (form previews, film, model blocks, export) | form rendering and the film editor work on Vulkan |
| 5 | Read-back consumers: screenshot, video recorder, eyedropper, pixel editor | screenshots and video work on Vulkan |
| 6 | Picking redesign without stencil (§5.4) | pickable forms work on Vulkan |
| 7 | Mixins re-pointed; Sodium; Iris with a Vulkan guard | the mod loads and behaves identically with `Graphics API = Prefer Vulkan` |
| 8 | Access widener entries translated and re-enabled one by one | no commented-out entries left |

Order matters: phase 1 is a hard gate, and phases 3–5 are where the Vulkan-specific failures
actually live.

## 7. Open questions

* **Launch-time backend selection.** Whether `--graphicsBackend VULKAN` remains a supported
  argument in 26.2 or is now only an in-game option — the in-game option is the documented route;
  the argument should be confirmed in the log before it is relied on in CI.
* **Parchment or community parameter names for 26.2.** With Yarn gone, whether the ecosystem
  settled on a parameter-name overlay for 26.2 was not checked.
* **`GpuFormat` support matrix.** Which `GpuFormat`s are guaranteed to be usable as colour
  attachments on the Vulkan backend (`RGB8_UNORM` in particular) needs a runtime check via
  `DeviceLimits.maxTextureSizeForFormat` / a failed pipeline compile.
* **Post-processing.** BBS's `assets/bbs/shaders/post/box_blur_opaque.fsh` and post chains were not
  yet checked against 26.2's `PostChain`/`PostPass` and the `post_effect/*.json` format.
* **`DeviceLimits.minUniformOffsetAlignment`** vs the uniform ring buffer BBS will want for its
  per-draw blocks — the vanilla `DynamicUniforms` storage already handles it, but a BBS-owned one
  would have to.
